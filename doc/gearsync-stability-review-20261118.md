# GearSync 稳定性评审：对照 GarSync 2.14.0 (8524)

2026-11-18 · GearSync 基线 `6394410` · 仅评审，未修改业务代码、未运行真实同步

## 结论

最值得借鉴的是 **确认目标端导入结果、保留每条活动的进度，以及对缺失或过期会话明确报错**。GearSync 不需要照搬 GarSync 的认证协议或整套同步框架。建议先修高驰链路中能直接复现的失败误报和丢重试问题，再用现有 SQLite 增加少量持久状态，最后统一 Garmin 上传的会话刷新和结果处理。

前一轮故障已修复：旧高驰 OSS 凭证地址返回 `404` HTML；`6394410` 改为从带认证的区域 Training Hub 获取 STS，并校验响应。前一轮已用中国区真实账号验证登录、取凭证和初始化 Ali OSS，但没有完成真实活动上传或确认青龙部署。本报告讨论的是 **STS 之后的导入** 和其他路径的同类风险，不建议再改一次已验证的新 STS 地址。

## 优先发现

| 优先级 | 现状证据与影响 | 建议 |
| --- | --- | --- |
| P0：失败被报成正常 | 高驰导入把响应直接当 JSON；模拟 `502` HTML 会执行 `exit()`，产生退出码 `0`，剩余活动被中断。列表遇到模拟 `401` JSON（没有 `data`）则返回空列表。中国区同步入口收到 `failed=1` 只发通知，进程仍正常退出。见 `scripts/coros/coros_client.py:89`、`:204`、`scripts/garmin_cn_to_coros.py:20`、`scripts/gear_sync.py:64`。 | 借鉴刚修好的 STS 校验：为高驰登录、列表、下载和导入统一校验 HTTP / 数据格式 / 业务结果，设连接和读取超时。区分无新活动与接口失败；客户端不直接 `exit()`，由两个 CLI 入口传播任务结果，配置错误或未处理失败返回非零；通知成败不改变同步结果。日志记录阶段、活动 ID、错误类型，不打印请求密钥。 |
| P0：临时失败失去重试，阶段结果互相覆盖 | 同一次模拟对象存储超时，Garmin 中国区仍保留 `pending=[101]`，国际区却写成 `is_sync=2`，而待同步查询只查 `0`。AWS 上传器吞掉 SDK 异常，代码仍向高驰提交导入；模拟导入返回 `True` 时甚至计成功。中国区本地删除失败也会出现“库里已完成、通知报失败”；国际区的广泛异常处理还可能把此前写入的成功覆盖为异常。见 `scripts/garmin/garmin_global_client.py:282`、`:302`、`scripts/db/activity_db.py:25`、`scripts/oss/aws_oss_client.py:33`、`scripts/garmin/garmin_cn_client.py:275`。 | OSS 上传必须确认成功才能进入导入；暂时故障保留可重试资格。清理警告不改变已确认的远端结果；记账失败不能计成功，也不能任由下次重复导入。共用 Garmin 中国/国际到高驰的阶段与错误定义，避免修一边漏一边。历史 `is_sync=2` 原因混杂，不批量改回 `0`；先列出并核对目标端。 |
| P1：受理、完成与写库没有区分 | Garmin 目标的多个方向碰到 HTTP `202` 或内层业务码 `202` 立即置为已同步，不区分携带完成结果和仅受理，现有测试甚至固定了空响应体 `202` 也成功。高驰 `result='0000'`、`data.status=2` 被压成布尔值，未保留任务 ID 或目标活动 ID；现有证据不能确定该状态是否永远是最终完成。见 `scripts/coros/coros_client.py:95`、`:315`、`scripts/garmin/garmin_cn_client.py:359`、`scripts/garmin/garmin_global_client.py:370`。 | 只有响应能证明完成、明确重复并匹配目标活动，或目标端查证已入库，才标成已同步。先在高驰中国区观察脱敏的真实单条响应，确认状态契约；同步返回终态时无需为了模仿 APK 强加轮询。已受理未确认、POST 读超时或中断则保留待核对；下一轮先查询或对账，不盲目重发。 |
| P1：Garmin 上传没有复用读路径的令牌检查 | 本地安装的 `garth==0.5.20` 给 `connectapi`、`download` 的 `api=True` 请求自动检查 OAuth2 过期。主上传路径手工 `requests.post`，直接取 `oauth2_token`；离线模拟显示，若已有缓存用户资料但令牌过期，中国与国际区都会发送旧令牌，不调用刷新。国际区还会对 `RequestException` 重试写入请求，但服务器可能已接收。见 `scripts/garmin/garmin_cn_client.py:51`、`:169`、`scripts/garmin/garmin_global_client.py:160`、`:190`。 | 统一上传前的有效会话检查，并保留 HTTP 状态、响应体和目标区域；读操作可以有限退避，写入结果不明先对账。凭据失效要和网络失败分开，确认为失效才刷新或有限重登；持久化会话时按账号和区域隔离，校验加载后的域名，不依赖缓存用户名判断授权。无需复制 APK 凭据或新增认证方式来修复这一点。 |
| P2：重复扫描、文件校验与并发 | 高驰分页给仍在时间窗内的每一条历史活动先取下载链接，再从 DB 筛待同步项；它还把“本页没拿到链接”当作扫描结束。Garmin 定时扫描每次从头开始，并按首次早于时间下限的记录提前结束。Garmin→高驰先上传原始下载字节，成功之后才尝试打开 ZIP；本地文件只按活动 ID 命名，任务并行可能互踩，SQLite 仅以查询后插入去重，表没有对应唯一约束。见 `scripts/coros/coros_client.py:235`、`:296`、`scripts/garmin/garmin_cn_client.py:115`、`:234`、`scripts/db/activity_db.py:15`、`:52`。 | 先抓元数据、筛待同步，再按需拿高驰下载链接；后续用明确时区、带重叠的增量扫描，并独立恢复旧待办。上传前识别真实 FIT 或合法 ZIP，按扩展名和内容选成员，不盲取首项；用临时文件加原子重命名，保留原文件字节和哈希。单机先加共用锁和 SQLite 唯一约束，而不是引入队列服务。切换账号时隔离记录与缓存，防止继承别的账号的完成状态。 |

补充：`scripts/coros/coros_client.py:63` 已保存区域 API，但查询、下载链接和导入仍使用 CN 的固定地址；对象存储使用凭证返回的 bucket，导入报文却从静态表组装 bucket 与 service。这是可见的不一致，不代表已证实国际区线上故障。先保持当前 CN 路径不变；只有确实需要高驰国际区时，再让区域化配置、上传回执和导入参数使用同一来源。若下载返回的是独立对象存储签名 URL，不应向未经确认的主机透传高驰访问令牌；当前 `download()` 会无条件附加高驰请求头，建议随请求层收口。

## 建议实施顺序与验收

1. **先做高驰链路的最小改动**：同时覆盖 Garmin 中国、国际到高驰的失败传播；已有 STS 地址保持不变。验收：`401`、`502` HTML、OSS 超时、单条失败、清理失败各自可辨，下一条可继续，待同步项不丢失，无新活动退出 `0`；真实有失败的任务能被青龙识别。
2. **再做恢复与对账**：以源活动、方向及账号为键，在现有 SQLite 持久化对象键、任务 ID、目标活动 ID、阶段和最近错误等实际需要的信息。写请求前记录提交意图，已受理或结果不明时先查证。带目标任务 ID 时用任务查询；无 ID 时仅用可靠的目标端匹配，否则标为待核对，而不是承诺恰好一次。兼容旧完成记录，不重扫或重发整库。验收：模拟“服务端收到请求但客户端超时”“已受理后进程退出”“远端已完成但本地写库失败”，恢复时优先查询，不重复 POST。
3. **扩展到 Garmin 目标和增量扫描**：修复过期会话后，再共用上传结果解析。首个真实验证只选一条明确未导入的中国区活动：核对高驰活动列表中确实存在、保存目标 ID，同一路径再次运行不新增活动；再按实际使用的方向扩大。不默认转换、修补坐标或改写设备信息。
